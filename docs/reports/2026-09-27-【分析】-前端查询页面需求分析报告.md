# 前端查询页面 需求分析报告

时间：2026-09-27　|　依据：用户留言（两类查询诉求）+ 现有交付物 `data/db/haf.db`
方法：对交付库做全量盘点与两类查询实测（脚本 `scripts/frontend_probe.py`，可复跑）
说明：本报告为**分析**，不含前端代码实现。

---

## 一、需求解读

用户明确的两类查询（**均为"最新"视角，不关心变更链本身**）：

| # | 诉求 | 本质 |
|---|---|---|
| ① | 了解**某类设备 / 某种设备**最新的相关许可证情况，含相关许可证、变更、详细参数 | 设备 → 许可证集合 → 最新参数 |
| ② | 了解**某单位**最新的相关许可证情况，含设备详细参数 | 单位 → 许可证集合 → 最新参数 |

**关键约束**：页面展示的是"**链尾快照**"——最新状态必须由变更链推导而来（不允许直接拼接历史表），但变更链本身不作主视图，仅作为附加入口（时间 / 摘要 / 明细 / 链接）。

**现状已满足该约束**：交付库中 `licenses.当前版本id` + 视图 `view_device_index`（只取当前版本范围行）即为"链尾快照"口径；本次实测确认两条查询路径全部走通。

### 2.3 两类查询实测

**① 设备维度**：`设备类别=阀门` → 18 品种 / 469 行 / 69 家单位；`品种=隔离阀` → **174 行 / 38 家单位**（同一单位因不同核安全级别与参数而多行）。
按生效日期倒序可真实反映"最新"：如 2026-09-18 延续件（浙江三方控制阀 设计/制造两证、上海阀门五厂等）。

**② 单位维度**：`中核苏阀` → 2 张证（设计 `S（26）17号`、制造 `Z（26）31号`），状态均为有效、有效期至 2031-09-30，版本 3/4 个、变更 1/2 次，最近变更摘要可读（如"制造证：新增 8 项设备范围；修改 1 项…"），当前版本设备参数 35 行（阀门）。

### 2.4 性能与部署形态实测

| 项 | 实测 |
|---|---|
| 设备条件查询 | 走索引 `idx_scope_var`（`SEARCH scope_items USING INDEX`） |
| 单位模糊查询 | 全表扫描 `licenses`（552 行，毫秒级，当前规模无压力） |
| 静态化体积 | `view_device_index` 552→2565 行 JSON **2.1MB**；`view_license_current` **433KB**；库文件 5.6MB |

## 三、页面结构建议

### 3.1 双入口

```
入口 A「按设备查」
  设备类别（46，带品种数/许可证数）
    └ 设备品种（190，带行数/单位数）
        └ 结果列表（按“最近更新”倒序）
             单位 | 证字号 | 证件类型 | 活动种类 | 状态 | 核安全级别 | 关键参数 | 最近更新 | 来源
             ↳ 同单位多行可折叠；可切换“只看有效”；可导出

入口 B「按单位查」
  单位搜索（406 家，支持模糊/规范化匹配）
    └ 单位卡片：该单位全部许可证（类型/证号/状态/有效期/最近更新/变更次数）
        ├ 设备参数（按设备类别分组，取当前版本）
        └ 变更记录（时间 / 摘要 / 明细可展开 / 官网链接 + 附件页码）
```

### 3.2 公共元素与交互要点

| 要素 | 说明 |
|---|---|
| 状态徽标 | 有效 / 无效 / 已注销 / 待核实；撤稿时附「来源文函官网已撤下」提示（`数据标志`） |
| 数据截止日期 | 取 L1 `meta.last_run`（页面必须显示，避免把旧数据当实时） |
| 来源可追溯 | 每条记录给「官网原文」+「附件页码」，可回跳核对 |
| 参数呈现 | **不做固定列**：参数键在不同设备类别下不同（通径/压力/温度 vs 结构形式/载荷等级 vs 材料/重量/壁厚），以"参数键值表 + 原文 JSON 展开"呈现 |
| 未标注处理 | 品种/级别缺失的行在类别入口可见，但标注「未标注品种/级别」，避免用户误以为无数据 |
| 变更 | 默认只显示最近一条摘要 + 次数；展开才看明细 diff（新增/删除/修改） |
| 境外单位 | 建议单独筛选（`证件类型=境外注册登记确认书`）或独立入口 |

## 四、需求 vs 现状的差距与改造建议

| # | 差距 | 影响 | 建议（L4 层派生，不改解析层） |
|---|---|---|---|
| G1 | 无设备层级字典：类别→品种清单靠前端 distinct | 筛选下拉、计数、级联交互需每次聚合 | 增加派生视图 `view_device_taxonomy`：`设备类别 / 设备品种 / 明细行数 / 单位数 / 最近更新日期` |
| G2 | 单位检索为 `LIKE` 全表扫描且**无规范化名**（括号/空格/曾用名差异会漏检） | 单位搜索命中率 | 增加 `licenses.单位规范化名` 派生列（复用 `chain.norm_unit` 规则）+ `view_unit_index`（单位、规范化名、证数、证件类型、最近更新） |
| G3 | **无统一"最近更新日期"**：需同时看 `生效日期` 与 `最近变更日期` | "最新"排序与"近期更新"标记 | 视图增加 `最近更新日期 = max(当前版本生效日期, 最近变更日期)` 与 `近期更新`（≤90 天）标记 |
| G4 | 状态默认口径未定 | 544 有效 vs 8 无效/注销 | 默认筛选"有效"，提供"包含无效/已注销"开关；页面明示筛选口径 |
| G5 | 覆盖度缺口（品种 279 行、级别 231 行缺失） | 按品种入口命中不全 | ① 前端按类别入口兜底展示；② 若需提升，执行 Q-L3-5（追加 LLM 补全，<0.2M token） |
| G6 | 参数列非标（不同类别键不同） | 表格设计 | 用键值表；`能力特征参数可读` 作为摘要列，`能力特征参数`(JSON) 作展开 |
| G7 | 变更"相关变更"入口未定义粒度 | 需求①提到"相关变更" | 设备/单位视图按 `license_id` 关联 `changes`：列表显示最近 1 条摘要 + 次数，卡片展开全部 |
| G8 | 排序字段无索引（按 `最近更新日期` 排序） | 规模小，暂非瓶颈 | 派生列落地后按需加索引（或物化排序结果） |
| G9 | 前端形态未定 | 部署方式 | 见 §5 方案对比 |
| G10 | 数据更新节律未在页面体现 | 用户可能误读时效 | 显示数据截止日期 + 「本周更新 N 条」摘要（来自 `parse_state.meta.last_summary`） |

## 五、前端形态方案对比（供决策）

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A 静态站点**（推荐起步） | 由 L4 额外导出 JSON 分片：`taxonomy.json` + `category_<类>.json`（按需加载）；纯 HTML/JS 前端，无后端 | 零运维、可离线、可直接挂到 workbuddy 资料库/轻应用 | 组合筛选弱、模糊搜索需前端自建索引 | 以"浏览 + 精确定位"为主的场景 |
| **B 轻后端** | 单文件服务（Python 标准库 `http.server` 或 FastAPI）只读 SQLite，提供 3~4 个查询接口 | 支持任意组合筛选/模糊搜索、口径统一、数据更新即刷新 | 需常驻进程 | 需要"搜索 + 多条件筛选"、多人使用 |
| **C 直连数据库** | workbuddy 以数据库连接方式查询（自然语言/BI） | 无前端开发量 | 依赖平台能力，交互不可控 | 内部快速验证 |

**量化依据**：`view_device_index` 全量 JSON 2.1MB（gzip 后约 300~400KB），分片加载后单页仅需 10~100KB —— **方案 A 完全可行**；若最终要求"输入关键词跨设备跨单位联合搜索"，则用方案 B。

## 六、接口契约（可直接落地为 SQL / API）

```sql
-- ①-1 设备类别/品种字典（G1）
SELECT 设备类别, 设备品种, COUNT(*) AS 明细行数, COUNT(DISTINCT 持证单位) AS 单位数,
       MAX(数据生效日期) AS 最近更新
FROM view_device_index GROUP BY 设备类别, 设备品种 ORDER BY 明细行数 DESC;

-- ①-2 某品种的最新许可证（按最近更新倒序，仅有效）
SELECT 持证单位, 证字号, 证件类型, 核安全级别, 能力特征参数, 能力特征参数JSON,
       数据来源事件, 数据生效日期, 官网链接, 附件页码
FROM view_device_index
WHERE 设备类别 = :类别 AND 设备品种 = :品种 AND 许可证状态 = '有效'
ORDER BY 数据生效日期 DESC;

-- ②-1 单位检索（G2：用规范化名匹配）
SELECT DISTINCT 单位名称 FROM view_unit_index WHERE 单位规范化名 LIKE '%' || :关键词 || '%';

-- ②-2 单位卡片
SELECT 证字号, 证件类型, 状态, 状态依据, 有效期止, 版本数, 变更次数,
       最近变更日期, 最近变更摘要, 数据标志, 官网链接, 附件页码
FROM view_license_current WHERE 单位名称 = :单位名 ORDER BY 证件类型;

-- ②-3 该单位的设备参数（当前版本）
SELECT s.设备类别, s.设备品种, s.核安全级别, s.能力特征参数, s.能力特征参数可读,
       s.活动场所, s.备注, s.源页码
FROM scope_items s JOIN licenses l ON l.license_id = s.license_id
WHERE l.单位名称 = :单位名 AND s.version_id = l.当前版本id
ORDER BY s.设备类别, s.设备品种;

-- ②-4（可选）相关变更
SELECT 变更日期, 变更摘要, 变更明细, 官网链接, 附件页码
FROM changes WHERE license_id = :license_id ORDER BY 变更日期 DESC;
```

**为落地上述接口需在 L4 增加的派生对象**（建议，非本次实施）：
`view_device_taxonomy`（G1）、`view_unit_index` + `单位规范化名`（G2）、`最近更新日期/近期更新`（G3）。

## 七、非功能需求

| 项 | 要求 |
|---|---|
| 性能 | 单查询响应 < 100ms（当前规模可轻松满足：设备查询走索引，单位查询全表 552 行） |
| 数据时效 | 页面显示"数据截止日期"；随周更（`--stage weekly`）更新；建议同时展示"本周更新条数" |
| 可追溯 | 所有展示项必须能回到官网原文 + 附件页码（当前 100% 具备） |
| 一致性 | 展示口径统一为"链尾快照"；禁止在页面拼接历史表导致状态与参数矛盾 |
| 容错 | 字段缺失显示"未标注"而非空白；撤稿数据打标提示而非隐藏 |
| 权限 | 若含境外单位/未公开内容需限内网；当前数据均为官网公开信息 |

## 九、结论

1. **数据侧已就绪**：两类查询所需字段 100% 具备（除状态类派生字段），且"最新"口径已由 `当前版本id` + `view_device_index` 天然实现，无需改动 L1~L3。
2. **需要补 3 个派生对象**（G1 设备字典、G2 单位检索视图/规范化名、G3 统一最近更新日期），均为 L4 建库层的小改动，可在前端开发启动前一次完成。
3. **形态建议**：以**方案 A（静态分片 JSON）**起步，若确认需要组合筛选/模糊搜索/导出，再升级为方案 B（轻后端只读 SQLite）。
4. **两个前置决策**：F5（形态与挂载入口）、F7（是否先补全品种/级别覆盖度）——确定后即可进入前端开发。
