## 二、开发中的修正（相对 M1 报告方案）

1. **注销内嵌规则改句界匹配**：原 `.{0,60}` 窗口在"同时注销俄罗斯Joint Stock Company Scientific…"（英文名 100+ 字符）场景漏标，改为 `同时注销[^。；\n]{0,200}?(许可证|确认书)`，8/8 全中。
2. **"颁发"规则收紧为仅认"颁发"字样**：原 `颁发|批准|准予` 在多标签语义下会给"关于**批准**延续…"误加"颁发"标签（虚高至 226）。实测 0 篇域内标题含"批准/准予"但无具体事件词，收紧无损失，且消除噪音。
3. **need_pdf_parse 判定简化为"有附件即 true"**：原方案（按事件/活动种类猜测）经真实数据核验不成立——变更类 87 篇中 61 篇（70%）带附件，明细位置无规律；"有附件"这一客观信号更泛用且无信息损失，M3 可自行跳过低价值件。

## 三、合并标签风险提示（应用户要求指出）

多标签合并（裁定 Q1-5）整体可行，但存在以下风险，下游（M2 及之后）使用时须注意：

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | **否定案例混入正面统计** | "不予延续"文档同时带"事件:延续"标签（标题两词都命中）。下游若直接 `count("事件:延续")` 统计延续业务量，会把否定案例算入 | 下游使用时先排除 `事件:不予延续`；或约定优先级：不予延续 > 延续 |
| R2 | **"变更"标签混合三种语义** | 许可活动范围变更（87）/ 注册登记范围变更（12）/ 单位名称变更（2）目前共用一个标签 | 暂可从 `match_reasons` 区分三者；若 M2 需要独立子标签（如"变更:范围"/"变更:名称"），请再裁定一次 |
| R3 | **关键词重叠噪音的一般性风险** | 公文措辞"批准/准予"等泛词与具体事件词天然重叠，本次已收紧"颁发"规则，但未来新文种可能出现类似问题 | 每条标签均附 `match_reasons`（规则名+位置+原句），出现可疑标签可即时定位；建议每轮增量后人工抽检 10~20 条 |
| R4 | **一函多事件的拆分归属** | 如"18 家单位延续+1 家注销"合并在一篇通知中，文档级标签无法区分每家单位对应哪个事件 | 属 L3 解析层职责（按单位拆记录），L2 只需保证事件不漏 |

## 四、M1 → M2 数据接口（契约，后续不建议大改）

`data/labeled_docs.json`：

```jsonc
{
  "meta": { "source", "generated_at", "rules_version", "input_count", "stats" },
  "documents": [
    {
      // L1 原始字段全部透传（doc_id 唯一键、名称、正文、附件及链接、…）
      "labels": ["事件:颁发", "事件:注销", "证件类型:许可证", "活动种类:制造"],  // 排序去重
      "match_reasons": ["事件[颁发]: 标题命中 '…'", "事件[注销]: 正文内嵌命中(换证时同时注销原证) '…'"],
      "need_pdf_parse": true   // 有附件即 true，M3 按需处理
    }
  ]
}
```

设计要点（泛用性）：
1. **透传不改动**：L1 字段原样保留，打标只增不改，L2 可独立重跑覆盖；
2. **域外不丢弃**：全部 567 篇都写入输出（域外 `labels=[]`），保证全量可追溯、需求边界变化时无需重爬；
3. **标签可扩展**：`类别:值` 格式，新增标签族（如 M2 需要的单位列表）只需加前缀，不破坏既有字段；
4. **接口稳定承诺**：`labels` / `match_reasons` / `need_pdf_parse` / 原始透传四项为契约字段，后续阶段按此消费。
