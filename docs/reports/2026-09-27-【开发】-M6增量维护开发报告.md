## 二、实现要点

### 2.1 增量状态（`haf/state.py`）
- 键 = **`文函doc_id|附件URL`**（同一附件 URL 可能被多篇文函引用，实测 1 个 URL 被 11 篇引用；若只按 URL 记录会串 doc_id）。
- 值 = `sha1`（下载时计算）、解析模式、记录数、解析时间。
- **模式敏感**：状态记录本轮是否启用 LLM；关闭 LLM 跑出的结果不用于启用 LLM 的轮次（反之亦然），避免误复用低质量结果。
- `records=0` 表示该附件本就无有效记录（如纯名单页），可直接跳过，不必重解析。
- 剪枝：不在本轮清单中的状态自动清理（官网撤下/文函关系变化）。

### 2.2 周更编排（`--stage weekly`）
`L1 采集（subprocess 复用 nnsa_crawler.py）→ L2 打标（全量、秒级）→ L3 增量解析 → L4 全量重建（秒级）`；
异常不中断整体流程（爬虫失败会抛出并终止，便于发现网络问题；L3 内部失败逐条隔离）。

### 2.3 撤稿 / 修订同步
| 环节 | 逻辑 |
|---|---|
| 发现 | L1 `--full-scan` 时，窗口内文函在列表中消失 → `site_status=missing_in_list`（不删除） |
| 传播 | L4 建库时：`documents.官网状态` 记录撤稿；`license_versions.文档状态=官网未见`；`licenses.数据标志=来源文函官网已撤下` |
| 降级 | 原判"有效"的许可证 → 状态改为**待核实**，`状态依据` 保留原因（不静默删除数据） |
| 视图 | `view_license_current` 暴露 `数据标志`；`view_device_index` 暴露 `来源文函状态` |

### 2.4 附件稳健性
- **PDF 文件头校验**：下载后校验 `%PDF-`，否则标记 `非PDF` 并跳过（实测 1 个：官网链接后缀为 .pdf 实为其他文件），避免每轮重试。
- L3 迭代口径改为**文函 × 附件**（而非唯一 URL），保证共享附件在不同文函下各自成记录。
- 块级失败隔离：单块异常写入 `block_error` 记录，不中断整份附件。

## 四、开发过程中修正的问题

| # | 问题 | 修正 |
|---|---|---|
| P1 | 关闭 LLM 的轮次产出的状态被启用 LLM 的轮次复用（质量下降） | 状态记录 `llm` 标志并纳入新鲜度判定 |
| P2 | 同一附件被多篇文函引用时，状态键只按 URL → 第 2+ 篇复用第一篇的记录（doc_id 串号） | 状态键改为 `doc_id\|url`；迭代口径改为文函×附件 |
| P3 | 无有效记录的附件（纯名单页）每轮都被重新解析 | 状态中以 `records=0` 记录，判定为"可跳过" |
| P4 | 非 PDF 文件（.pdf 后缀）每轮解析失败并重试 | 下载时校验文件头 → 标记 `非PDF` 并跳过 |
