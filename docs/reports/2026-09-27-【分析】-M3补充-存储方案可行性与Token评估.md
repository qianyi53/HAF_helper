## 一、workbuddy database 多表 / 外键 / 视图 调研结论

### 1.1 调研结果

| 问题 | 结论 | 来源与可靠性 |
|---|---|---|
| 资料库（workbuddy database）支持哪些数据格式 | **CSV、Markdown、HTML**（5.3.11 起为"AI 原生格式"），另有 Word/Excel/PPT；JSON 未提及 | 腾讯云开发者社区《WorkBuddy 资料库》解读文（🟡 中，产品解读非官方规范） |
| 资料库是否支持多表 JOIN / 物理外键 | **未找到任何官方或可靠说明**；资料库的"数据表"以 **CSV 为后端底座**，描述集中在"HTML 前端 ↔ 单张 CSV 双向同步"，未提及跨表 JOIN/外键 | 同上（🟡 中）；另有第三方描述"数据管理→表关联"可定义逻辑关联（🔴 低，来源含反爬/内容质量存疑） |
| 是否支持视图（View） | **未确认** | 🔴 低（相关文章付费墙截断） |
| workbuddy 能否直连真实数据库 | **能**：支持 MySQL / PostgreSQL / SQL Server / Oracle / 达梦等，配置连接串；自然语言查询流程含"数据库元数据学习（表名、字段、类型、**主外键关系**）" | CSDN 实战指南（🟡 中，且为第三方教程），与 CodeBuddy 官方文档"MCP 可接入数据库工具"一致 |
| CodeBuddy/WorkBuddy 官方文档 | 官方用户指南中数据库相关仅两句：①云服务集成（CloudBase/Supabase/CloudStudio）实现数据库管理；②MCP 可接入数据库作为 AI 工具。**无表结构/外键/视图的规范文档** | 🟢 高（codebuddy.ai 官方文档） |

### 1.2 判断与应对

**不能假定 workbuddy database 支持物理外键与视图**。因此方案改为**平台无关的三形态交付**，无论平台能力如何都能落地：

| 形态 | 内容 | 适配场景 | 说明 |
|---|---|---|---|
| **A. CSV 分表包（主交付）** | 6 张逻辑表各一个 CSV，主键列 + **逻辑外键列**（关联键以列值携带，如 `license_id`、`version_id`、`doc_id`），配套 `数据字典.md` 声明外键关系 | 资料库/轻应用直接导入（CSV 已确认支持） | 即便平台不识别外键，靠键值仍可做关联与核对 |
| **B. 物化宽表（可读性视图，主交付）** | `view_license_current.csv`、`view_device_index.csv` 两张**已算好的宽表**（CSV 不能存 VIEW，故物化） | 任何平台的"打开即读"、看板/检索 | 直接满足"主数据可读性强"的要求 |
| **C. SQLite 单文件 + DDL（可选）** | `haf.db`：含物理外键 + 真正的 `VIEW`；另附 MySQL/PostgreSQL 建表脚本 | workbuddy 通过"数据库连接"方式直连（已确认支持主流关系库） | 单文件零部署；若平台只支持 MySQL/PG，用附带的 DDL 一键建库导入 |

> **建议**：待 Q-L4-1（workbuddy database 实际导入方式与规范）确认后，从 A/B 起步（覆盖面最广），若平台确实支持数据库连接再补 C。三形态共用同一份解析结果，切换成本仅为导出环节。

## 二、方案修订（按裁定与需求细化）

### 2.1 变更点

| 项 | 原方案 | 修订后 | 依据 |
|---|---|---|---|
| 单位表 `units` | 有 | **删除**；单位"最新名称"直接冗余到各表；历史名称可选保留 `曾用名` 列（仅用于版本链衔接，可去） | 需求细化：单位信息别处可查，保留最新名称即可 |
| 可读性 | 仅规范表 | **新增 2 张物化视图表**（许可证可读主表 + 设备可读检索表） | Q-L3-2（2） |
| 外键 | 假定物理外键 | **逻辑外键**（列值关联 + 数据字典声明）+ 可选 SQLite 物理外键 | Q-L3-2（1）调研结论 |
| 交付形态 | 单文件 | **三形态（CSV 分表 / 物化宽表 / SQLite+DDL）** | 同上 |

### 2.2 修订后的表结构（6 表 + 2 视图表）

| 表 | 粒度 | 主键 | 逻辑外键 | 要点 |
|---|---|---|---|---|
| `documents` 文函 | 一文档一条 | `doc_id` | — | L1/L2 全字段 + 解析状态、块数、附件页码索引 |
| `licenses` 许可证 | 一证一条 | `license_id`（稳定 ID） | `doc_id`、`version_id` | `单位名称(最新)`、`曾用名(可选)`、`证字号(当前)`、证件类型、活动种类JSON、**状态**[有效/无效/不予延续/已注销]、状态依据doc_id、发证日期、有效期起/止/原文、设备类别汇总JSON、核安全级别汇总、**官网链接、附件链接、附件页码** |
| `license_versions` 版本 | 每次颁发/延续/变更一版 | `version_id` | `license_id`、`doc_id` | 来源事件、生效日期、附件URL、页码起止、范围行数、`change_id`(若变更) |
| `scope_items` **设备粒度明细** | 一行设备一记录 | `scope_item_id` | `version_id`、`license_id` | 设备种类(可空)、**设备类别**、**设备品种**、核安全级别、**能力特征参数JSON**、主要关键工艺、活动范围及完成形式、活动场所、备注原文、分包项目JSON、源页 |
| `changes` 变更记录 | 一变更通知一记录 | `change_id`(=变更doc_id) | `license_id` | 变更日期、变更类型、摘要、**变更明细JSON{新增[],删除[],修改[{字段,before,after}]}**、官网链接、附件页码、置信度 |
| `registry_scopes` 境外注册登记范围 | 一行一记录 | `registry_scope_id` | `version_id` | 同 `scope_items` 字段映射（设备品种/设备名称、活动类别、表一/表二） |
| **`view_license_current`** 视图表 | 一行一证 | `license_id` | — | 可读宽表：单位名称、证字号、证件类型、活动种类、状态、有效期起止、设备类别(顿号串)、核安全级别、最近变更时间+摘要、官网链接、附件页码 |
| **`view_device_index`** 视图表 | 一行 = 设备类别×品种×许可证 | — | `license_id` | 可读检索表：设备类别、设备品种、核安全级别、**最新制造/设计能力特征参数（可读串 + JSON 双列）**、持证单位、证字号、状态、官网链接、附件页码 |

**可读性设计要点**：视图表列名用中文、多值用顿号串联、能力参数同时给"可读串"（如 `DN≤1050 / P≤8.9MPa / T≤320℃`）与原始 JSON 双列，兼顾人读与机读。

**许可证主键**：`license_id` 取"规范化单位名 + 证件类型"的稳定摘要（延续换证导致证字号变化时链不断），`证字号` 为版本属性（M3 报告第四节 4.5）。

## 三、Token 评估（实测，非估算）

### 3.1 实测方法

1. 对 10 个样本 PDF（125 页 / 56 块 / 266 行范围明细）逐页构造"送 LLM 的载荷"（页文本 + 表格 markdown），用 **tiktoken o200k_base** 实测 token；
2. 按方案锚点切块（一证一块 / 一页一家），测块级输入；
3. 按修订后 schema 构造"块级输出 JSON"，实测固定部分与每行明细的输出 token；
4. 用全量估算（**820 块 / 2224 页 / ≈3895 行**）外推三情景。

### 3.2 实测基础数据

| 项 | 实测值 |
|---|---|
| 中文 token 比 | ≈ **0.67 token/字符**（o200k_base 实测） |
| 每页载荷 | ≈ **452 tok** |
| 每块正文（含表格） | ≈ **953 tok** |
| 块头（文档/附件/页范围/证字号） | ≈ **158 tok** |
| 提示词（抽取指令 + schema 说明） | ≈ **260 tok** |
| 输出·固定部分（证书级字段 JSON） | ≈ **261 tok** |
| 输出·每行范围明细（含能力参数 JSON） | ≈ **219 tok** |
| 每块平均行数 | ≈ **4.8 行** |

### 3.3 全量 2021 以来（820 块 / 2224 页）评估

| 情景 | 输入 | 输出 | 合计 |
|---|---|---|---|
| **S1 全量块过 LLM** | **1.12M tok** | **1.16M tok** | 2.28M tok |
| S1 + 1.3× 重试/复检开销 | 1.46M tok | 1.51M tok | 2.97M tok |
| **S2 规则优先 + 30% 块 LLM 兜底** | **0.34M tok** | **0.35M tok** | 0.69M tok |
| S2 + 1.3× 开销 | 0.44M tok | 0.45M tok | 0.90M tok |
| S3 规则优先 + 10% 兜底 | 0.11M tok | 0.12M tok | 0.23M tok |
| S3 + 1.3× 开销 | 0.15M tok | 0.15M tok | 0.30M tok |
| 变更摘要（P1，101 篇） | ≈ 0.08M tok | ≈ 0.05M tok | 0.13M tok |

**结论**：即使**全量块都过 LLM（S1）**，总量也在 **2.3M tok 量级**（含重试约 3M），属极小规模；按推荐的 **S2（规则优先 + 兜底）** 仅 **0.7M tok 量级**。单次全量解析的 LLM 成本可忽略，**瓶颈不在 token 而在解析准确率的迭代**。

**口径说明**：token 数基于 `o200k_base`（GPT-4o 系）。若换成其他 tokenizer（如 Claude/Qwen 系），中文比例可能相差 ±15%~25%，量级结论不变。

> **更正 M3 主报告**：主报告第一节/第六节曾估"P0 全量约 2.0M tok、兜底约 0.6M"——那是按 2.5k tok/块的粗估；本报告为实测口径（1.37k tok/块输入、1.42k tok/块输出），以本报告为准。

## 四、LLM 接入占位符设计（本次不实现，仅约定）

待 L3 开发时按此落地，需求方只需填入 key 即可：

| 项 | 约定 |
|---|---|
| 配置文件 | 项目根 `config.local.json`（**加入 .gitignore**，不入库）：`{provider, base_url, api_key, model, temperature, max_tokens, concurrency, timeout, max_retries}` |
| 环境变量（优先级更高） | `HAF_LLM_API_KEY`、`HAF_LLM_BASE_URL`、`HAF_LLM_MODEL` |
| 读取顺序 | env → `config.local.json` → 缺失则明确报错退出（不静默降级） |
| 模板文件 | L3 开发时提供 `config.example.json`（仅字段与注释，无密钥） |
| 调用入口 | 单一入口（如 `haf/llm.py`）集中处理超时/重试/限速/日志，便于替换供应商 |
| 缓存 | `data/llm_cache/`（键=块内容 hash）：重跑不重复计费，便于对比提示词版本效果 |
| 试用方式 | 需求方填 key 后，可先只跑 20 块做提示词调优，再全量 |
