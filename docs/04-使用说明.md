# 使用说明

面向操作者：如何跑通、如何周更、如何调参、如何排查。

## 1. 环境准备

```powershell
cd E:\workspace\HAF_info
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt          # 运行时依赖仅 pdfplumber（L3/L4）
```

**唯一需要配置的是 LLM 密钥**（占位符，按优先顺序读取）：

| 顺序 | 位置 | 说明 |
|---|---|---|
| 1 | 环境变量 `HAF_LLM_API_KEY` / `HAF_LLM_BASE_URL` / `HAF_LLM_MODEL` / `HAF_LLM_TIMEOUT` / `HAF_LLM_MAX_TOKENS` | 部署/CI 推荐 |
| 2 | 项目根 `config.local.json` | 复制 `config.example.json` 填入 `api_key` 即可 |

`config.local.json` 可用字段：`provider` / `base_url` / `api_key` / `model`（默认 `deepseek-flash`，自动关闭思考链）/ `thinking` / `temperature` / `max_tokens` / `timeout` / `max_retries`。

> **密钥安全**：`config.local.json` 已在 `.gitignore`，**不要提交**；未配置 key 时程序会明确报错（不静默降级），此时可用 `--no-llm` 走纯规则路径。

## 2. 全流程命令

```powershell
# 周更一键（推荐）：L1 采集 → L2 打标 → L3 增量解析 → L4 重建交付库
python -X utf8 -m haf.pipeline                       # 等价于 --stage weekly

# 分阶段
python -X utf8 -m haf.pipeline --stage l1            # 仅官网增量采集
python -X utf8 -m haf.pipeline --stage l2            # 仅筛选打标
python -X utf8 -m haf.pipeline --stage l3            # 仅 PDF 解析（增量）
python -X utf8 -m haf.pipeline --stage l4 --csv      # 仅建库（+CSV 分表）
python -X utf8 -m haf.pipeline --stage all           # L2+L3+L4（不抓官网）
```

实测耗时：全量首跑 ≈3 分钟（289 个附件）；**增量周更 ≈16 秒**（附件无变化时 0 解析、0 LLM 调用）。

## 3. 参数速查

| 参数 | 适用阶段 | 含义 |
|---|---|---|
| `--no-llm` | L3 | 纯规则，不调用 LLM（用于对照/断网） |
| `--llm-only` | L3 | 所有块都走 LLM（仅对照实验用，成本高） |
| `--reparse` | L3 | 忽略增量状态，强制重解析全部附件 |
| `--limit N` | L3 | 只新解析前 N 个附件（调试） |
| `--csv` | L4 | 额外导出 `data/db/csv/*.csv` 分表 |
| `--full-scan` | L1 | 从 cutoff 起全窗校验（可发现撤稿） |
| `--since YYYY-MM-DD` | L1 | 修改起始日期（cutoff） |
| `--delay 秒` | L1/L3 | 请求间隔（默认 1.5s，礼貌抓取） |

单独调爬虫（L1 全参数）：`python -X utf8 scripts/nnsa_crawler.py --help`

## 4. 产物清单

| 文件 | 层 | 说明 |
|---|---|---|
| `data/nnsa_policy_docs.json` | L1 | 全量文函（567 篇） |
| `data/labeled_docs.json` | L2 | 打标结果（含域外排除项，全量可追溯） |
| `data/pdf/<doc_id>/*.pdf`、`data/pdf/_index.json` | L3 | 附件与下载索引（含 sha1） |
| `data/parse_state.json` | L3 | 增量状态（文函\|附件 → 指纹/模式） |
| `data/parsed_records.json` | L3 | 解析记录 + 组装模型（≈10MB，可重生成） |
| `data/db/haf.db` | L4 | **交付物**：SQLite（6 表 + 2 视图 + 外键） |
| `data/db/csv/*.csv` | L4 | 可选分表导出 |
| `data/llm_cache/` | — | LLM 结果缓存与用量文件（`_usage.json`） |
| `frontend/index.html` | L5 | 浏览器版单页（查云数据库；已发布至应用站点） |
| `frontend/wechat/核安全设备许可证查询.html` | L5 | 微信版单页（数据内嵌 ~1.5MB，构建产物） |
| `frontend/haf-sync/last-sync-report.json` | L5 | 云同步报告（每次 sync.mjs 运行生成） |

## 6. 交付库使用示例

```sql
-- ① 某单位的许可证状态与最近变更
SELECT 单位名称, 证字号, 证件类型, 状态, 有效期止, 变更次数, 最近变更日期, 最近变更摘要, 官网链接
FROM view_license_current WHERE 单位名称 LIKE '%中核苏阀%';

-- ①b 逐条变更（含 diff 明细 JSON 与附件页码）
SELECT c.变更日期, c.变更摘要, c.变更明细, c.官网链接, c.附件页码
FROM changes c JOIN licenses l ON l.license_id = c.license_id
WHERE l.单位名称 LIKE '%中核苏阀%' ORDER BY c.变更日期 DESC;

-- ② 按设备类别/品种查最新能力参数
SELECT 设备类别, 设备品种, 核安全级别, 能力特征参数, 持证单位, 证字号, 许可证状态, 官网链接, 附件页码
FROM view_device_index WHERE 设备类别 = '阀门' AND 设备品种 LIKE '%隔离阀%';

-- ③ 按单位定位证字号 + 变更编号 + 原文链接 + 附件页
SELECT l.单位名称, l.证字号, c.change_id AS 变更编号, c.官网链接, c.附件页码
FROM licenses l LEFT JOIN changes c ON c.license_id = l.license_id
WHERE l.单位名称 LIKE '%江苏翔淳%';
```

现成脚本：`python -X utf8 scripts/l4_verify.py`（三个诉求演示）、`scripts/l4_quality.py`（质量指标）。

## 7. 常见场景

| 场景 | 操作 |
|---|---|
| 首次建库 | `--since 2021-01-01` 跑 L1 → `--stage weekly` |
| 修改起始日期 | `python scripts/nnsa_crawler.py --since 2024-01-01`（cutoff 写入 meta，L2/L3 自动适配） |
| 官网撤稿核查 | `--stage l1 --full-scan` → L3/L4 会把来源撤稿的许可证标 `数据标志` 并降级为「待核实」 |
| 换 LLM 或改提示词 | 直接改配置/`haf/prompts.py` → 运行 L3（模式变化会自动重解析；必要时加 `--reparse`） |
| 重新计费规避 | LLM 结果按块缓存，重跑同一块零消耗；`data/llm_cache/_usage.json` 可查累计用量 |
| 只重算数据库 | `--stage l4`（秒级，不重新解析 PDF） |

## 9. 故障排查

| 现象 | 原因与处理 |
|---|---|
| `pip` 报 `Fatal error in launcher: ... D:\workspace\HAF_app\...` | venv 从旧设备整目录迁移后，`Scripts\*.exe` 启动器内嵌**旧机器的绝对路径**（`python.exe` 走 pyvenv.cfg 不受影响）。处理：删除 `.venv` 后重建——`C:\Python314\python.exe -m venv .venv`，再 `pip install -r requirements.txt tiktoken`（tiktoken 供 M3 分析脚本用） |
| `缺少 LLM API key` | 三处配置均未找到；按第 1 节配置，或加 `--no-llm` 走纯规则 |
| 某附件解析失败 | 记入 `parsed_records.json` 的 `meta.errors`，下轮自动重试；`.pdf` 但非 PDF 的文件已在下载时标记 `非PDF` 并跳过 |
| 附件被反复重解析 | 检查该附件是否本就无有效记录（如纯名单页）——已在状态中以 `records=0` 记录，正常不会重解析 |
| 数据里少了某单位 | 看 `labeled_docs.json` 是否命中域门控；再看该文函的第 4 类排除规则（见业务逻辑说明 §2） |
| 需要清理重来 | 删 `data/parse_state.json`（全量重解析）或 `data/pdf/_index.json`（重下载） |

## 10. 注意事项

- **抓取礼貌**：默认 1.5s/请求；全量首跑约 3 分钟，勿用 `--delay 0`。
- **密钥安全**：`config.local.json`（LLM）与 `frontend/haf-sync/config.json`（云同步密钥）均不入 git；提交前确认 `git status` 无密钥文件（`config.example.json` 为无密钥模板，可入库）。
- **可复跑**：所有阶段幂等，产物可整体重生成；`data/parsed_records.json` 与 `data/pdf/` 不入 git（体积大且可重生成），`data/db/haf.db`、CSV 与 `frontend/wechat/*.html` 作为交付物入库。
- **两个发布入口**：浏览器版与微信版数据同源同口径；改完数据先 `haf-sync` 同步（浏览器版），再重建重发微信版（详见第 5 节）。
